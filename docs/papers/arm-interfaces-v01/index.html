Native interface contracts and bounded CPU mechanics benchmark

Arm interfaces and simulation-only skill installation

31 October 2026 · DVIDIA

54/54 numerically valid · 21,654 state rows · 0 audit mismatches · simulation only

Source & history · Download Markdown

Abstract

Three pinned native simulation interfaces describe PiPER, SO-101, and UR5e with Robotiq 2F-85, preserving each arm and gripper command’s native units. A frozen 54-attempt roster covers three motion cases, three command periods, and two deterministic repeats; 21,654 state rows and 1,260 commands are retained, with zero audit mismatches. Twenty-one offline computation windows exceed their nominal command period; this is not a hardware timing measure. A data-only lift gate uses caller-declared bounds and is not connected to the controller. The existing PiPER policy remains 5/12 versus its authored teacher at 12/12; no new learning, cross-arm transfer, or physical qualification is claimed.

One local command now describes three native simulation adapters, checks a learned policy against its exact embodiment, installs its data, and runs an independently scored attempt. The same package includes a common tracking benchmark and a small environment-conditioned lift-planning assessment.

This is a research preview. The three adapters are PiPER, SO-101, and UR5e with a Robotiq 2F-85. Only PiPER has a learned policy runner in this installer. No physical arm is connected, calibrated or qualified by these commands.

Install locally

Use Python 3.12 and a fresh virtual environment. This preview is source branch feat/arm-interfaces-v01; the existing stable package and previous preview do not contain dvidia-arm.

git clone --branch feat/arm-interfaces-v01 https://github.com/Dvidia-Inference/dvidia-training.git
cd dvidia-training
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install '.[arm]'
dvidia-arm list
dvidia-arm describe piper

The CPU simulator needs no CUDA GPU. Setup requires network access; commands use local, verified assets after provisioning. Hardware minimums and other OS performance are unqualified. A browser UI could call the same Python functions; this preview adds Terminal commands, not a browser control surface or hardware connection.

Three explicit command contracts

AdapterArm axesGripper commandAvailable here
piper6, radiansOne coupled finger slide target in metres; not total jaw gapNative mechanics and existing learned block policy
so1015, radiansGripper hinge angle in radiansNative mechanics; no learned task runner
ur5e-2f856, radiansRobotiq native actuator input, 0–255; not metres or newtonsNative mechanics; no learned task runner in this installer

Asset identity, ordered actuator names, units, couplings, limits, native version and compiled model identity travel with the adapter. Unknown commands, wrong units/order, nonfinite values and limit violations are rejected. Named command inputs require the complete exact name set. No driver is selected from a model file and no downloaded code is executed.

Provision the already pinned models with dvidia-robot-sim fetch piper and dvidia-robot-sim fetch so101, each with --output robot-assets. The UR5e and Robotiq reference uses dvidia-embodiment fetch-assets --output reference-assets, documented in hardware-reference.md in the source branch. Different roots can be passed to the shared benchmark using --reference-assets.

Check, install, then run

Use the published PiPER block policy. The exact initial release model is:

curl --fail --location 'https://huggingface.co/Dvidia/piper-block-placement-v01/resolve/10edc19c63f04d1428e051787a601e5b69d8a3f5/model/model.json?download=true' --output model.json
printf '%s\n' '2976a605575d9edefb5db366e72c5e006c0ce85a5531ad3d61512436864c8ded  model.json' | shasum -a 256 -c -
dvidia-arm check --model model.json --robot piper
dvidia-arm install --model model.json --robot piper --assets robot-assets --output installed-placement
dvidia-arm inspect installed-placement --assets robot-assets
dvidia-arm run installed-placement --assets robot-assets --start-x .309 --start-y -.04 --goal 1 --output placement-attempt

install verifies and copies data without taking physics steps. run checks the installation again, then uses the existing bounded PiPER runner and retains the trace and independent score. A failed attempt remains a failed attempt. The output directory must be new. Changing the policy, runtime, assets or contract requires a new installation. The same policy on --robot so101 or --robot ur5e-2f85 is rejected, even though UR5e also has six arm axes.

This policy was distilled from synthetic controller demonstrations. The frozen held-out placement result remains 5/12, versus 12/12 for the authored teacher. A fresh installed-wheel smoke used Python 3.12 in isolated site-packages with PYTHONPATH unset; the wheel SHA-256 was e8b03e4d718dde277d467f7fcca97b5540620fbf03b737b5a34ec3ff4b4ae8f9. The one selected example at start x=0.309 m, y=−0.04 m, goal 1 completed the native runner and independent scorer with 12.003 mm endpoint error. Wrong-arm and hardware checks exited 2. On the shared host, full control-step compute p95 was 34.924 ms and 179 of 1,000 nominal 20 ms compute budgets were exceeded. This does not qualify real-time behavior. This checks packaging and rejection paths for the published example; it is not a new held-out benchmark or physical qualification. The frozen policy's operating envelope is a 40 g rigid block, initial x=0.284–0.314 m and y=−0.045–−0.015 m, and two known destinations. The published feed-forward primitive uses initial native object position, goal and time. It has no learned camera or contact recovery.

Measure accuracy and compute separately

dvidia-arm benchmark --assets robot-assets --reference-assets reference-assets --output tracking-study

The shared protocol exercises hold, smooth arm motion and gripper cycling, at 10, 20 and 40 ms control updates with a fixed 1 ms physics step. It preserves all attempts and compares joint tracking error, gripper tracking in its native units, terminal-link tracking and loop compute percentiles. Compilation and loop compute are separate costs. These are unloaded simulated mechanics, not object-placement success, sensor-to-actuator latency or physical accuracy.

Do not increase a learned policy's speed merely by replaying it faster. Its training clock, acceleration, contact, braking and recovery requirements need a new task benchmark. Optimize on development scenes, freeze the choice, then evaluate untouched confirmation scenes. Report the accuracy/compute tradeoff and failures rather than collapsing unlike units into a single ranking.

Frozen native mechanics run

The fixed roster covers PiPER, SO-101 and UR5e/Robotiq; each has hold, arm perturbation and gripper-cycle cases, at 10, 20 and 40 ms command periods, with two deterministic repeats. All 54 scheduled attempts are numerically valid. The traces retain 21,654 state rows at 1 ms spacing and 1,260 issued commands. An independent audit reports zero mismatches. Twenty-one unpaced computation windows exceed their nominal command period. This count measures the recorded offline loop, which includes stepping, state snapshots and reference forward kinematics; it is not a hardware deadline-miss count. Repeats and state rows are retained engineering evidence, not independent task trials or a statistical estimate. The study measures unloaded command tracking and compute only; it does not score an object task, learn a new policy, or compare physical accuracy.

The existing PiPER learned block policy remains 5/12 on its frozen task test, versus 12/12 for its authored teacher. The installation example reuses that policy; it is not new training or new held-out evidence. SO-101 and UR5e have mechanics interfaces here, but no learned task runner in this installer.

A skill needs a suitable scene

For state x, estimated physical properties theta, embodiment r and task g, applicability is a set A(g, r, theta). The controller should transport only while its estimated state and uncertainty satisfy the task's conditions. Probing changes the estimate of theta; it is not evidence that the original estimate was correct. A new object, pose or grasp can invalidate earlier evidence.

The first planning gate uses a deliberately limited vertical, two-finger friction model:

required force = mass upper bound × (gravity + upward acceleration) × safety factor
friction capacity = 2 × friction lower bound × allowable normal force per finger

It also checks declared reachability, gripper fit, pose uncertainty, freshness, slip, calibration identity and a pose-specific payload ceiling. Unknown mass or friction remains unknown. Supplied measurements are caller assertions; the tool does not authenticate a calibration or measure a robot.

dvidia-arm task-template > lift-conditions.json
dvidia-arm assess-task lift-conditions.json

Results are blocked, probe_required, test_lift_required, or ready_for_simulated_transport. This assessment performs no sensing or motion and is not wired into the existing learned block controller. It omits moments, center of mass, deformation, contact damage dynamics and impacts. The input normal-force budget must already respect the object's allowable load and the gripper's calibrated capability. A real runtime needs time-aligned evidence, force limits, slip monitoring and bounded recovery before using this decision.

The next experiment is to vary object mass, friction, center of mass and sensor delay independently, then compare an unconditional lift with probe → small lift → transport/regrasp/abstain. Measure drops, false secure-grip decisions, overload, completion, recovery time and observation-to-command latency. Preserve failure conditions, especially when probing cannot resolve uncertainty.

Expansion roadmap

Add adapters by interface family, then qualify each exact arm/gripper pairing. The following are integration candidates, not supported DVIDIA hardware. Planned references include the LeRobot SO-100 documentation and ROS 2 hardware interface documentation:

PriorityCandidate familyUpstream interface to build on
FirstSO-100, SO-101; later KochLeRobot robot interface, with distinct motor maps and per-device calibration
FirstPiPER and its firmware variantsAgileX CAN SDK and ROS 2 driver
NextOpenArm, later bimanual configurationsLeRobot OpenArm guide, CAN and distinct arm/hand calibration
NextUFACTORY xArm variantsVendor ROS 2 packages
NextFranka research armsVendor ROS 2 integration
NextInterbotix / WidowX familyVendor manipulator packages

ros2_control provides a common hardware-component vocabulary. It does not erase joint limits, transmission, firmware, tool, sensor, or task differences. Published software interfaces also do not establish that every robot's manufacturing design is open source. Review each dependency's actual license before integration.

Every new adapter needs a pinned asset/driver inventory, named units and frames, calibration mapping, stale-state/limit/stop tests, a native mechanics receipt, and a task-specific policy evaluation. Physical support requires measured hardware evidence. Cross-arm transfer remains a separate learning and retargeting problem; it cannot be solved by renaming joint fields.
